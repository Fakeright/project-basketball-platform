# COURTSIDE Reuse Team Players During Team Creation Design

## Goal

ทำให้ผู้จัดการ/โค้ชสามารถเลือกผู้เล่นที่บัญชีเคยใช้ในทีมเดิม แล้วคัดลอกข้อมูล
เข้าเป็นรายชื่อเริ่มต้นของทีมใหม่ได้ขณะสร้างทีม โดยเลือกเป็นรายคน เลือกทั้งหมด
ในทีมต้นทาง หรือเลือกทั้งหมดทุกทีมได้ พร้อมรักษาประวัติของทีมเดิมไม่ให้เปลี่ยนแปลง

## Context

ปัจจุบัน `TeamPlayer` เป็นข้อมูลรายชื่อที่อยู่ภายใต้ทีมหนึ่งทีมและไม่ผูกกับบัญชี
`PLAYER` ผู้จัดการ/โค้ชหนึ่งบัญชีสามารถเป็นเจ้าของหลายทีม แต่เมื่อสร้างทีมใหม่
ต้องสร้างทีมก่อนแล้วจึงกรอกข้อมูลผู้เล่นอีกครั้งใน Team Workspace

ฟีเจอร์นี้เพิ่มการนำข้อมูลเดิมกลับมาใช้โดยไม่เปลี่ยน `TeamPlayer` เป็นฐานข้อมูล
ผู้เล่นกลาง และไม่เปลี่ยนกติกาที่ผู้เล่นไม่จำเป็นต้องมีบัญชี COURTSIDE

## Scope

ระยะนี้ประกอบด้วย:

1. แสดงคลังผู้เล่นจากทุกทีมที่บัญชีปัจจุบันเป็นเจ้าของในหน้าสร้างทีม
2. รวมผู้เล่นคนเดิมที่เคยอยู่หลายทีมเป็นรายการเดียว
3. รองรับการค้นหา เลือกรายคน เลือกทั้งหมดรายทีม และเลือกทั้งหมดทุกทีม
4. แสดงทีมต้นทางและสถานะปัจจุบันหรือเคยนำออก
5. คัดลอกผู้เล่นที่เลือกเป็นแถวข้อมูลที่แก้ไขได้ก่อนบันทึก
6. เพิ่มผู้เล่นใหม่ด้วยการกรอกเองร่วมกับผู้เล่นที่เลือกได้
7. สร้างทีมและผู้เล่นเริ่มต้นไม่เกิน 30 คนใน transaction เดียว
8. รองรับการสร้างทีมที่ยังไม่มีผู้เล่นเช่นเดิม

ระยะนี้ไม่รวม:

- การสร้างโมเดลผู้เล่นกลางหรือการเชื่อมผู้เล่นกับบัญชี `PLAYER`
- การแก้ข้อมูลผู้เล่นครั้งเดียวแล้วกระจายไปยังหลายทีม
- การย้าย `TeamPlayer` ระหว่างทีม
- การนำเข้าด้วย CSV
- การจับคู่ข้อมูลด้วยเลขบัตรประชาชน เอกสาร หรือข้อมูลชีวมิติ
- การเปลี่ยนแปลงประวัติ `TeamMember` เดิม

## Player History Identity

ระบบสร้างรายการประวัติจาก `TeamPlayer` ทั้ง active และ inactive ของทุกทีมที่
ผู้ใช้ปัจจุบันเป็นเจ้าของ โดยรวมรายการด้วยค่าที่ normalize แล้วของ:

- ชื่อ
- นามสกุล
- วันเกิด

การ normalize ตัดช่องว่างหัวท้ายและเปรียบเทียบตัวอักษรโดยไม่แยกตัวพิมพ์ใหญ่เล็ก
วันเกิดเปรียบเทียบในรูปแบบวันที่ `YYYY-MM-DD` ผู้เล่นที่มี identity เดียวกันในหลายทีม
แสดงเพียงหนึ่งรายการ พร้อมชื่อทีมต้นทางทั้งหมด

รายการที่รวมแล้วเลือกข้อมูลตั้งต้นจาก record ที่แก้ไขล่าสุด หากเวลาเท่ากันให้เรียง
ด้วย id เพื่อให้ผลลัพธ์ deterministic สถานะเป็น `ใช้งานอยู่` เมื่อมี record ต้นทาง
อย่างน้อยหนึ่งรายการที่ active มิฉะนั้นเป็น `เคยนำออก`

การรวมนี้เป็นเพียง presentation/application view ไม่สร้าง global player id และไม่
แก้ relation ของฐานข้อมูล ผู้ใช้ยังแก้ snapshot ก่อนสร้างทีมใหม่ได้

## Authorization And Privacy

- ต้องมี session และ permission `team.create`
- Query ประวัติด้วย `ownerId` ของ actor ปัจจุบันเท่านั้น
- Platform Admin ไม่เห็นข้อมูลจากบัญชีอื่นโดยอัตโนมัติในหน้าสร้างทีม
- Client ได้รับ view-ready history เท่าที่จำเป็นสำหรับการเลือกและแก้ข้อมูล
- Server ไม่เชื่อถือ ownership จาก id ที่ client ส่งกลับ
- คำขอสร้างทีมส่งข้อมูลผู้เล่น snapshot ที่ผ่านการแก้ไขแล้ว ไม่ส่งคำสั่งให้ย้าย
  หรือแก้ record ต้นทาง
- Audit event ของการสร้างทีมและรายชื่อบันทึกเฉพาะ metadata ที่ไม่ใช่ PII เช่น
  team id และจำนวนผู้เล่น ห้ามบันทึกชื่อ วันเกิด ชื่อเล่น หรือเบอร์โทร

## User Experience

### Team Identity

หน้าสร้างทีมยังมีชื่อทีม จังหวัด และรูปแบบ `5v5`/`3v3` ตามเดิม ส่วนรายชื่อผู้เล่น
อยู่ถัดลงมาในหน้าเดียวกันและไม่ซ้อน card หลายชั้น

### Historical Player Selector

- ปุ่ม `เลือกจากผู้เล่นเดิม` เปิดพื้นที่เลือกรายชื่อ
- มีช่องค้นหาชื่อ นามสกุล และชื่อเล่น
- แสดงผู้เล่นแยกตามทีมต้นทาง พร้อม checkbox `เลือกทั้งหมด` ประจำทีม
- มี checkbox `เลือกทั้งหมดทุกทีม`
- คนเดียวกันที่ปรากฏในหลายทีมใช้ selection state เดียว เลือกแล้วถูกเพิ่มเพียงครั้งเดียว
- แสดงชื่อทีมต้นทางทั้งหมดและสถานะ `ใช้งานอยู่` หรือ `เคยนำออก`
- ตัวเลือกทั้งหมดมี label ที่ screen reader เข้าใจได้ และใช้งานด้วยแป้นพิมพ์ได้
- สถานะ checkbox แบบเลือกบางส่วนใช้ indeterminate state
- เมื่อการเลือกจะเกิน 30 คน ระบบไม่เพิ่มรายการที่เกินและแสดงจำนวนที่ต้องลด

### Initial Roster Editor

ผู้เล่นที่เลือกถูกคัดลอกเข้าส่วน `รายชื่อที่จะเพิ่ม` และแก้ข้อมูลได้ก่อนบันทึก
ผู้ใช้เพิ่มแถวว่างเพื่อกรอกผู้เล่นใหม่ หรือนำแถวที่เลือกออกได้ การแก้ snapshot
ไม่เปลี่ยนข้อมูลในทีมต้นทาง

Desktop ใช้ตารางที่มีขนาดคอลัมน์คงที่ตามรูปแบบฟอร์ม roster ปัจจุบัน Mobile
ใช้ส่วนกรอกแนวตั้งที่มีเส้นแบ่งชัดเจน หน้าไม่เกิด horizontal overflow และข้อความ
ข้อผิดพลาดไม่ทำให้ control เปลี่ยนขนาดจนทับส่วนอื่น

ผู้ใช้สามารถสร้างทีมโดยไม่มีผู้เล่นได้ หากมีผู้เล่นต้องมีอย่างน้อยหนึ่งแถวที่สมบูรณ์
และมีได้สูงสุด 30 คน

## Validation

ใช้กฎเดียวกับ `TeamPlayer` ปัจจุบัน:

- ชื่อ นามสกุล และวันเกิดเป็นข้อมูลบังคับ
- วันเกิดต้องไม่อยู่ในอนาคต
- เบอร์เสื้อเป็นจำนวนเต็ม 1-999 หรือเว้นว่าง
- ตำแหน่งเป็น `PG`, `SG`, `SF`, `PF`, `C` หรือเว้นว่าง
- ชื่อเล่นและเบอร์โทรเป็นข้อมูลไม่บังคับและใช้ความยาวสูงสุดเดิม
- identity `ชื่อ + นามสกุล + วันเกิด` ต้องไม่ซ้ำใน roster ที่กำลังสร้าง
- เบอร์เสื้อที่ระบุต้องไม่ซ้ำใน roster ที่กำลังสร้าง
- payload ผู้เล่นมีได้ 0-30 คน

Client validation ใช้เพื่อช่วยแก้ข้อมูล แต่ server validation เป็น authoritative
ข้อผิดพลาดระดับช่องแสดงใกล้ช่องที่เกี่ยวข้อง พร้อม summary ภาษาไทยและ focus ไปยัง
ข้อผิดพลาดแรก

## Application And Data Flow

### Load Team Creation Page

1. Server Component อ่าน actor จาก session
2. Application use case ตรวจ `team.create`
3. Repository อ่านทีมและ `TeamPlayer` ทั้ง active/inactive เฉพาะ `ownerId` ของ actor
4. Application layer รวม identity และสร้าง view model ที่มี source teams กับ status
5. Server Component ส่ง view-ready history ให้ Client Component

ไม่ต้องเพิ่ม public GET endpoint สำหรับประวัติ เพราะข้อมูลใช้เฉพาะหน้าสร้างทีมที่
render ฝั่ง server

### Submit Team And Initial Players

1. Client ส่งข้อมูลทีมและ `players` snapshot ไป `POST /api/teams`
2. Route Handler parse payload ด้วย Zod และตอบ `422` เมื่อโครงสร้างไม่ถูกต้อง
3. `createTeam` ตรวจจังหวัด permission และกฎ roster ทั้งหมด
4. Repository transaction สร้าง Team แล้วเพิ่มหรือคืนสถานะ TeamPlayer ตามกฎเดิม
5. บันทึก audit metadata ภายใน transaction เดียวกัน
6. หากขั้นตอนใดล้มเหลว transaction rollback และไม่เหลือทีมเปล่าจากคำขอนั้น
7. เมื่อสำเร็จตอบ `201` พร้อม Team และ TeamPlayer ที่สร้าง แล้วนำผู้ใช้ไป Team Workspace

การสร้างทีมเปล่ายังคงส่ง `players: []` ได้และใช้ transaction เดียวกัน

## Architecture

รักษาทิศทาง dependency เดิม:

```text
presentation -> application -> domain
infrastructure -> application/domain contracts
```

- Domain มีชนิดข้อมูล historical player identity และกฎ deduplication/validation
  ที่ไม่ import React, Next.js หรือ Prisma
- Application มี use case สำหรับอ่าน player history และขยาย `createTeam` ให้ประสาน
  การสร้าง roster แบบ atomic
- Infrastructure ขยาย TeamRepository สำหรับอ่าน player history ตาม owner และสร้าง
  Team พร้อม TeamPlayer ภายใน transaction
- Presentation เพิ่ม selector/editor ใน TeamEditor และขยาย schema ของ Route Handler

ไม่เพิ่ม Prisma model หรือ migration สำหรับฟีเจอร์นี้ เพราะข้อมูลเดิมเพียงพอและ
snapshot ใหม่ยังเก็บเป็น `TeamPlayer` ภายใต้ทีมใหม่

## Failure Mapping

- `401` ไม่มี session
- `403` ไม่มี permission หรือพยายามใช้ข้อมูลนอก ownership boundary
- `409` identity หรือเบอร์เสื้อซ้ำ หรือเกิด conflict จากข้อจำกัดฐานข้อมูล
- `422` payload ไม่ถูกต้อง ข้อมูลผู้เล่นไม่ครบ วันเกิดผิด หรือเกิน 30 คน
- `500` ความล้มเหลวที่ไม่คาดคิด โดย log เฉพาะ context ที่ไม่ใช่ PII

การโหลดประวัติล้มเหลวต้องแสดง error state ของหน้าสร้างทีม ไม่แสดงรายการว่างจนผู้ใช้
เข้าใจผิดว่าไม่มีประวัติ หากไม่มีประวัติจริงให้แสดง empty state และยังกรอกผู้เล่นใหม่ได้

## Testing

### Domain And Application

- รวม identity ซ้ำจากหลายทีมและเลือก record ล่าสุดแบบ deterministic
- สถานะ active เมื่อมี source record อย่างน้อยหนึ่งรายการ active
- รวม source team โดยไม่ซ้ำและเรียงผลลัพธ์คงที่
- จำกัด query เฉพาะทีมของ owner ปัจจุบัน
- ไม่รวม `TeamMember` เดิมเป็น player history
- สร้างทีมเปล่าได้
- สร้างทีมกับผู้เล่น 1-30 คนได้แบบ atomic
- ปฏิเสธผู้เล่นคนซ้ำ เบอร์เสื้อซ้ำ ข้อมูลผิด และจำนวนเกิน 30
- rollback ทีม ผู้เล่น และ audit เมื่อขั้นตอนใดล้มเหลว

### Route Handler

- ตรวจ `401`, `403`, `409`, `422` และ `201`
- ยอมรับ `players: []`
- ปฏิเสธ payload ผู้เล่นเกิน 30 คนหรือข้อมูลไม่ครบ
- ไม่ส่งรายละเอียด PII ใน error diagnostics

### UI

- ค้นหาด้วยชื่อ นามสกุล และชื่อเล่น
- เลือกและยกเลิกรายคน
- เลือกทั้งหมดรายทีมและเลือกทั้งหมดทุกทีม รวม indeterminate state
- คนเดียวกันจากหลายทีมเข้าสู่ roster เพียงครั้งเดียว
- แสดงสถานะ active/inactive และทีมต้นทาง
- แก้ snapshot เพิ่มแถวใหม่ และนำแถวออกได้
- แสดงข้อผิดพลาดรายช่องและ focus ข้อผิดพลาดแรก
- สร้างทีมโดยไม่มีผู้เล่นได้

### Verification

- รัน focused tests ระหว่าง TDD แล้วรัน test suite ทั้งหมด
- รัน lint, production build, Prisma validation และ `git diff --check`
- ตรวจ responsive ที่ประมาณ 375px, 768px และ 1440px

## Acceptance Criteria

1. ผู้จัดการ/โค้ชเห็นเฉพาะผู้เล่นจากทีมที่ตนเป็นเจ้าของ
2. รายชื่อรวมทั้งผู้เล่น active และผู้เล่นที่เคยนำออก พร้อมสถานะชัดเจน
3. ผู้เล่น identity เดียวกันจากหลายทีมถูกเพิ่มเข้า roster ใหม่ไม่เกินหนึ่งครั้ง
4. เลือกรายคน เลือกทั้งหมดรายทีม และเลือกทั้งหมดทุกทีมได้
5. ผู้เล่นที่เลือกแก้ไขหรือนำออกก่อนบันทึกได้ และกรอกผู้เล่นใหม่ร่วมกันได้
6. สร้างทีมเปล่าหรือสร้างพร้อมผู้เล่นสูงสุด 30 คนได้
7. Team, TeamPlayer และ audit สำเร็จหรือ rollback พร้อมกันทั้งหมด
8. การสร้างทีมใหม่ไม่แก้ข้อมูลหรือสถานะในทีมต้นทาง
9. Server บังคับ permission, ownership และ validation ครบถ้วน
10. หน้าใช้งานได้โดยไม่ซ้อนทับหรือเลื่อนแนวนอนที่ viewport เป้าหมาย
