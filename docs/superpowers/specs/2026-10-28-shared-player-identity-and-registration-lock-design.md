# COURTSIDE: ตัวตนผู้เล่นร่วมและการกันลงแข่งขันซ้อน

วันที่: 28 ตุลาคม 2026

## เป้าหมาย

ผู้จัดการทีมที่เลือก "ผู้เล่นเดิม" ต้องได้ตัวตนผู้เล่นคนเดิมในฐานข้อมูล ไม่ใช่คัดลอกข้อความไปสร้างคนใหม่ ผู้เล่นหนึ่งคนอาจมีความสัมพันธ์กับหลายทีมของผู้จัดการคนเดียวกัน แต่การส่งใบสมัครแข่งขันต้องไม่จองผู้เล่นคนเดียวกันไว้ในรายการที่ยังไม่สิ้นสุดมากกว่าหนึ่งรายการ

## สภาพปัจจุบันและข้อขัดแย้ง

- `TeamPlayer` เก็บชื่อ นามสกุล วันเกิด และข้อมูลทีมในแถวเดียว ปุ่มเลือกผู้เล่นเดิมสร้างแถว `TeamPlayer` ใหม่โดยส่งค่าข้อความเดิม
- `Registration` เก็บทีมและรายการ แต่ไม่เก็บรายชื่อผู้เล่น ณ วันที่สมัคร หน้าผู้จัดอ่าน roster ปัจจุบันของทีม จึงเปลี่ยนได้ภายหลัง
- แผนเดิม `2026-08-12-courtside-reuse-team-players` ระบุการคัดลอก snapshot ที่แก้ได้ ข้อกำหนดใหม่นี้แทนพฤติกรรมนั้นโดยตรง
- ข้อมูลจริงรวมถึงทีมที่เพิ่งสร้าง 16 ทีมและใบสมัครเดิม ต้องย้ายโดยไม่ลบทีม ผู้เล่น หรือผลการแข่งขัน

## แนวทางที่พิจารณา

1. **ตัวตนผู้เล่นกลาง + สมาชิกทีม + roster ใบสมัครที่ตรึงไว้ (เลือกใช้):** เพิ่ม `PlayerIdentity` ที่มีรหัสถาวรในบัญชีผู้จัดการเดียวกัน ให้ `TeamPlayer` เป็นสมาชิกทีมอ้างรหัสนั้น และเพิ่ม `RegistrationPlayer` เพื่อบันทึกตัวผู้เล่นและข้อมูลที่ใช้สมัคร ณ เวลาส่งใบสมัคร ใช้รหัสกลางตรวจซ้ำข้ามทีม/รายการ ข้อเสียคือ migration และการแก้ use case หลายจุด
2. **เชื่อม `TeamPlayer` กันด้วย source ID:** แก้ schema น้อยกว่า แต่การคัดลอกในอดีตมีหลายแถวที่ไม่รู้ต้นทาง โซ่อ้างอิงแก้ชื่อ/ลบแถวแล้วไม่มั่นคง และอธิบายกฎกันซ้อนได้ยาก จึงไม่เลือก
3. **ห้ามเลือกผู้เล่นเดิมระหว่างที่ทีมใดสมัครอยู่:** ทำง่าย แต่ยังไม่มีตัวตนร่วมจริงและไม่แก้ปัญหาสำเนาข้อความ จึงไม่เลือก

## ขอบเขตตัวตนและข้อมูล

- `PlayerIdentity` เป็นข้อมูลคนในขอบเขตเจ้าของทีม (`ownerId`) มี `id`, ชื่อ, นามสกุล, วันเกิด และคีย์ค้นหาที่ normalize ชื่อ/นามสกุลและวันเกิด ไม่ใช้เพียงชื่อเป็นตัวตน
- `TeamPlayer` คง `id` เดิมและข้อมูลเฉพาะทีม เช่น เบอร์เสื้อ ตำแหน่ง สถานะใช้งาน และประวัติ เพิ่ม FK ไป `PlayerIdentity` คนเดียวกันอาจมีหลาย membership แต่การเลือกจากประวัติจะไม่สร้าง `PlayerIdentity` ใหม่
- ข้อมูลชื่อ/วันเกิดเดิมใน `TeamPlayer` เก็บเพื่อความเข้ากันได้ระหว่างย้ายและเป็น snapshot ทางประวัติ แต่หน้าจอและกฎใหม่อ่านตัวตนกลางเป็นหลัก การแก้ชื่อ/วันเกิดต้องทำที่ตัวตนกลางภายใต้สิทธิ์เจ้าของ และไม่เปลี่ยน roster ที่ส่งสมัครไปแล้ว
- หนึ่งทีมมีสมาชิกที่ใช้งานอยู่ของ identity เดียวกันได้คนเดียว เบอร์เสื้อยังต้องไม่ซ้ำในทีมตามกฎเดิม
- ผู้เล่นคนละบัญชีที่ชื่อและวันเกิดเหมือนกัน **ยังไม่ถือเป็นคนเดียวกัน** เพราะระบบไม่มีเอกสารยืนยันตัวตนหรือกลไกอ้างสิทธิ์ร่วมข้ามบัญชี ห้ามอ้างว่ากันซ้อนข้ามบัญชีได้แน่นอน
- ภายในบัญชีเดียวกัน หากชื่อ นามสกุล และวันเกิดที่ normalize ตรงกัน ให้ถือเป็นคนเดียวสำหรับข้อมูลเก่าและข้อมูลใหม่ กรณีคนละคนที่ข้อมูลชุดนี้ตรงกันจริงต้องตรวจและแก้เป็นรายกรณี ไม่เดาตัวตนจากเบอร์เสื้อ

## การเลือกผู้เล่นและสร้างทีม

- หน้าเลือกผู้เล่นเดิมส่ง `PlayerIdentity.id` ของเจ้าของบัญชีไปที่ API; server ตรวจว่า identity นั้นเป็นของผู้จัดการทีม ไม่รับชื่อ/วันเกิดจาก client ไปใช้แทนตัวตน
- ผู้เล่นใหม่ยังกรอกชื่อ นามสกุล วันเกิดได้ ระบบหา identity เดิมในบัญชีเดียวกันก่อนสร้าง เพื่อไม่ให้คนเดิมเกิดซ้ำโดยไม่ตั้งใจ
- แก้เบอร์เสื้อ/ตำแหน่งเป็นข้อมูลของสมาชิกทีมนั้น; การแก้ชื่อ/วันเกิดของคนเดิมมีผลต่อ profile กลาง แต่ roster ใบสมัครที่ส่งแล้วไม่เปลี่ยนตาม
- การเอาผู้เล่นออกจากทีมปิด membership เฉพาะทีมนั้น ไม่ลบตัวตนกลางหรือสมาชิกในทีมอื่น

## การจองตัวผู้เล่นตอนสมัคร

- เมื่อส่งสมัคร สร้าง `RegistrationPlayer` ใน transaction เดียวกับ `Registration` โดยเก็บ `playerIdentityId`, `teamPlayerId` และ snapshot ชื่อ วันเกิด เบอร์เสื้อ ตำแหน่ง ณ เวลาสมัคร
- ใช้ผู้เล่นที่ active ทั้งทีมตามฟอร์มสมัครเดิม ไม่เพิ่มหน้าคัดผู้เล่นต่อรายการในรอบนี้ ทีมเดียวกันจึงยังส่ง roster ชุดเดียวกันไปหลายรายการที่เปิดพร้อมกันไม่ได้
- ก่อนสร้างใบสมัคร ตรวจทุก identity ใน roster ที่กำลังส่งกับ `RegistrationPlayer` ของใบสมัครอื่นในสถานะ `PENDING` หรือ `APPROVED` ซึ่งรายการยังไม่ `COMPLETED`/`ARCHIVED` หากพบให้คืน `409` พร้อมข้อความไทยที่ชี้ว่าผู้เล่นติดรายการอื่น (ไม่เปิดเผยข้อมูลรายการของบัญชีอื่น)
- ใบสมัคร `REJECTED`, `CANCELLED`, `WITHDRAWN` ปล่อยตัวทันที รายการ `COMPLETED`/`ARCHIVED` ปล่อยตัวแม้ใบสมัครเดิมยัง `APPROVED`
- ตรวจภายใต้ transaction แบบ Serializable และล็อก identity ตามลำดับ ID ก่อนตรวจซ้ำ เพื่อกันคำขอสมัครพร้อมกันสองรายการผ่านพร้อมกัน; ทดสอบกรณีแข่งขันกันจริง
- รายชื่อในหน้าผู้จัดของใบสมัครใหม่อ่าน `RegistrationPlayer` ไม่ใช่ roster ปัจจุบัน การเปลี่ยนสมาชิกทีมภายหลังไม่เปลี่ยนรายชื่อที่ส่งแล้ว
- ผู้จัดอนุมัติ/ปฏิเสธตามใบสมัครเดิม; การอนุมัติไม่ต้องจองซ้ำเพราะเริ่มจองตั้งแต่ `PENDING` การยกเลิก/ถอนใช้สถานะใบสมัครปล่อยสิทธิ์โดยไม่ลบ snapshot

## ย้ายข้อมูลจริง

1. ตรวจจำนวนทีม ผู้เล่น และใบสมัครก่อนทำ migration; บันทึกผลและเตรียมวิธีย้อนกลับ/สำรองข้อมูลตามสภาพแวดล้อม ห้ามใช้ `db push` หรือ reset บนฐานข้อมูลจริง
2. Migration แบบเพิ่มตาราง/คอลัมน์ก่อน: จัดกลุ่ม `TeamPlayer` ภายใน owner เดียวกันด้วยชื่อ–นามสกุลที่ normalize และวันเกิด สร้าง identity เดียวต่อกลุ่ม แล้วเติม FK ทุกแถว คง `TeamPlayer.id` และข้อมูลเดิมทั้งหมด
3. ตรวจ collision และจำนวนหลัง backfill; หาก identity ของบัญชีเดียวกันมีข้อมูลกีฬาแตกต่างกัน ให้คงค่ารายทีม ไม่เอาข้อมูลจากทีมหนึ่งทับอีกทีม
4. สำหรับใบสมัคร `PENDING`/`APPROVED` ที่ยังจองตัวอยู่ สร้าง `RegistrationPlayer` จาก roster ที่มีอยู่ ณ เวลาย้ายและระบุว่าเป็น backfill ซึ่งไม่อาจพิสูจน์รายชื่อ ณ วันที่เคยสมัครได้ ใบสมัครเก่าที่จบแล้วคงการแสดงผลเดิมเมื่อไม่มี snapshot
5. ตรวจคำขอสมัครที่อาจชนกันอยู่แล้วก่อนบังคับกฎ; รายงานรายการที่ต้องตัดสินด้วยคน ไม่ยกเลิกใบสมัครหรือแก้ผลการแข่งขันอัตโนมัติ
   ใบสมัครเก่าที่ชนกันคงอยู่ แต่บล็อกใบสมัครใหม่ที่ใช้คนเดียวกันจนกว่าจะปล่อยตัวตามสถานะ
6. Deploy schema และ code ตามลำดับที่ปลอดภัย ทดสอบบน development ก่อน production โดยมี migration ที่ทำซ้ำอย่างควบคุมได้ และตรวจยอดหลัง deploy

## สิทธิ์และการแสดงผล

- ผู้จัดการทีมอ่าน/เลือก identity ได้เฉพาะบัญชีตนเอง; admin override ต้องมี audit ตามกฎเดิม
- API ไม่ไว้ใจ `playerIdentityId` จาก client โดยตรงและไม่เปิดเผยข้อมูลส่วนตัวของผู้เล่นบัญชีอื่น
- UI แสดงตัวเลือกผู้เล่นเดิมพร้อมสถานะว่าติดใบสมัครอยู่หรือไม่ และแจ้งสาเหตุจาก server เมื่อกดสมัคร; server เป็นผู้ตัดสินจริง
- หน้าทีมยังแสดงชื่อ เบอร์ ตำแหน่ง และอายุเดิม; หน้าผู้จัดแสดง snapshot ใบสมัครโดยไม่เพิ่มเบอร์โทรศัพท์หรือวันเกิดเกินจำเป็น

## สิ่งที่ไม่ทำในรอบนี้

- ไม่สร้างบัญชี login ให้ผู้เล่นทุกคน ไม่เพิ่มการยืนยันตัวตนด้วยบัตรประชาชน
- ไม่รับรองการจับคู่คนเดียวกันข้ามผู้จัดการทีมคนละบัญชี
- ไม่แก้ผลการแข่งขัน สาย หรือตารางย้อนหลัง ไม่ลบข้อมูลเก่า
- ไม่เพิ่มการเลือกผู้เล่นรายรายการ; ทีมเดียวกันจะสมัครหลายรายการที่จองผู้เล่นพร้อมกันไม่ได้เพราะส่ง active roster ทั้งทีมเสมอ แต่หลายทีมของเจ้าของเดียวกันสมัครพร้อมกันได้เมื่อใช้คนละชุด

## การทดสอบและเกณฑ์เสร็จ

- Tests: backfill identity, คนเดิมหลายทีม/เบอร์เสื้อต่างกัน, เลือกเดิมโดย ID, ห้ามใช้ ID ต่าง owner, เพิ่มใหม่ไม่สร้างคนซ้ำ, membership inactive, อายุ/จำนวนทีมเดิม
- Tests: สมัครครั้งแรก, สมัครอีกทีมในรายการเดียวกัน/ต่างรายการถูก 409, pending/approved ล็อก, rejected/cancelled/withdrawn/completed ปล่อย, snapshot ไม่เปลี่ยนตามการแก้ทีม, concurrent requests
- Route/UI tests ครอบคลุมข้อความผิดพลาดภาษาไทย การเลือกผู้เล่นเดิม และหน้าผู้จัด; ตรวจ responsive 375/768/1440
- รัน focused tests, full tests, lint, build, migration dry run และตรวจฐานข้อมูล/เว็บจริงตามสิทธิ์ที่อนุมัติ ก่อนสรุปว่าใช้งานได้
